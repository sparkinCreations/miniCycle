# Service Worker Update Strategy

**Version:** 2.249 (June 2026)
**Last Updated:** June 2026
**Problem Solved:** Users with old cached service workers and modules not receiving updates

> For full offline boot architecture, caching layers, and iOS-specific issues, see **[PWA_OFFLINE_ARCHITECTURE.md](./PWA_OFFLINE_ARCHITECTURE.md)**.

---

## The Problem

### Original Issue (v1.326)
Users had old service workers that:
- Were cached by the browser (preventing updates)
- Didn't have `updateViaCache: 'none'`
- Never detected new versions (missing periodic update checks)

### Module Cache Duplication (v1.329–1.330)
Dynamic imports loaded modules **without** version parameters while HTML loaded them **with** (`?v=1.329`). This created two cache entries per module — the service worker cached both, so users stayed stuck on old versions even after an update.

**Root Cause:** Inconsistent URL patterns across import methods.

### Offline Boot Destruction (v2.050–2.056)
When a user reopened the PWA offline, the boot sequence misclassified import failures as cache corruption and triggered destructive recovery — deleting the only cached files available. This made the app unrecoverable until the user reconnected. See [PWA_OFFLINE_ARCHITECTURE.md](./PWA_OFFLINE_ARCHITECTURE.md) for the full diagnosis.

### Stale Build vs Network Version (v2.249)
`globalThis.APP_VERSION` comes from `version.js`, which the service worker serves **network-first** whenever a request's `?v=` doesn't match the deployed version. So `APP_VERSION` can read the **latest deployed** version even while the HTML/CSS actually rendered are a **stale cached older build**. Because `verifyVersionFresh()`, the About dialog, and "Check for Updates" all trusted `APP_VERSION`, none could detect stale HTML/CSS — a device could be stuck rendering an old build while every signal reported "up to date."

**Real symptom:** loaded HTML `<meta name="app-version">` = 2.247 with duplicate CSS, while About reported 2.248.

**Root Cause:** Trusting a network-fresh signal (`APP_VERSION`) as the "what am I running" truth, when the honest signal is the version baked into the loaded HTML.

## The Solution (6-Part Strategy)

### 1. version.js — Single Source of Truth
```javascript
// version.js — auto-generated by update-version.sh
globalThis.APP_VERSION = '2.249';
globalThis.CACHE_VERSION = 1092;
```

- One file, loaded first by the browser and inlined into the service worker
- All contexts (window, SW, modules) reference the same version
- `update-version.sh` keeps everything in sync

### 2. Versioned Module Imports with `withV()` Helper
```javascript
// orchestrator.js
const APP_VERSION = globalThis.APP_VERSION || 'dev-local';
const vParam = `?v=${APP_VERSION}`;

// All boot imports use vParam
const { coreBoot } = await import(`./modules/boot/coreBoot.js${vParam}`);

// coreBoot creates withV() and passes it to featureBoot → moduleLoader
const withV = (path) => `${path}?v=${effectiveVersion}`;
```

Every module import uses the **same versioned URL**, so a version increment invalidates all caches simultaneously with no duplicate entries.

### 3. Offline Retry: Drop `?v=` When Offline
```javascript
// orchestrator.js — version suffix logic
if (isRetry && navigator.onLine) {
    versionSuffix = `${APP_VERSION}.r${bootAttempt}`;  // Retry suffix forces re-fetch
} else if (isRetry && !navigator.onLine) {
    versionSuffix = '';  // Drop version — use browser HTTP cache
} else {
    versionSuffix = APP_VERSION;
}
const vParam = versionSuffix ? `?v=${versionSuffix}` : '';
```

When offline, retrying with a different `?v=` suffix would miss every cache. Instead, the retry drops the version parameter entirely so the browser's HTTP cache (24-hour `max-age`) can serve files.

The `withV()` helper propagates this through the entire chain: orchestrator → coreBoot → featureBoot → moduleLoader → all modules.

### 4. Version Parameter on SW URL
```javascript
navigator.serviceWorker.register(`./service-worker.js?v=${APP_VERSION}`, {
    updateViaCache: 'none'
});
```

Changing the URL forces the browser to fetch a new file, bypassing the cache.

### 5. Automatic Old SW Cleanup
```javascript
// Detect and remove old service workers without version parameter
const existingRegistrations = await navigator.serviceWorker.getRegistrations();
for (const reg of existingRegistrations) {
    const scriptURL = reg.active?.scriptURL || reg.waiting?.scriptURL;
    if (scriptURL && scriptURL.includes('service-worker.js') && !scriptURL.includes('?v=')) {
        await reg.unregister();
    }
}
```

Automatically migrates users from the old unversioned system.

### 6. Periodic Update Checks
```javascript
// Check every 60 seconds when tab is visible
setInterval(() => {
    if (!document.hidden && registration) registration.update();
}, 60000);

// Also check on tab focus
document.addEventListener('visibilitychange', () => {
    if (!document.hidden && registration) registration.update();
});
```

Users see updates within 60 seconds of deployment.

### 7. Immediate Version Freshness Check (`verifyVersionFresh()`)

An inline script in `miniCycle.html` runs immediately at boot, on every focus/visibility change, on `pageshow`, and on the `app:verifyVersion` event:

```javascript
// Fetches version.js with cache-buster — bypasses SW cache entirely
const response = await fetch(`./version.js?_cb=${Date.now()}`, {
  cache: 'no-store'
});
// The ACTUAL running BUILD = the HTML's baked <meta name="app-version"> (via getBuildVersion())
const buildStale     = serverVersion && buildVersion && buildVersion !== serverVersion;
const versionJsStale = serverVersion !== APP_VERSION ||
                       serverCacheVersion !== String(CACHE_VERSION);
if (buildStale || versionJsStale) {
  // Clear all caches + unregister the SW, then reload to ?_cb=<timestamp>
}
```

**Build version (v2.249):** The **build version** is the version baked into the loaded HTML's `<meta name="app-version">` tag — the honest "what am I actually running" signal, read by the new global `window.getBuildVersion()` (an inline script right after `version.js`). It is distinct from network-fresh `APP_VERSION`, which the SW serves network-first on a `?v=` mismatch. `verifyVersionFresh()` now ALSO compares **build (meta) vs the freshly-fetched server `version.js`**. If `build !== server` (`buildStale`), it self-heals: clears ALL caches, unregisters the SW, and reloads to `?_cb=<timestamp>`. This catches the "stuck on cached HTML while `version.js` says latest" state the old `APP_VERSION`-only check was blind to.

**Loop guard:** A per-session flag (`sessionStorage['__miniCycle_buildHeal']`, keyed on the server version) prevents reload loops when the cache can't refresh (e.g. flaky network). `sessionStorage` clears on a full app close, so a fresh launch retries. A newer deploy (different server version) still triggers a heal.

**Why both versions:** After deployment, the new SW may precache the updated `version.js` (making `APP_VERSION` match), but old modules are still served from the old SW's dynamic cache. `CACHE_VERSION` catches this — the loaded modules have the old cache version while the server has the new one. The pre-existing `APP_VERSION`/`CACHE_VERSION` mismatch path is preserved alongside the build check.

**SW bypass:** `version.js?_cb=<timestamp>` requests are intercepted by the SW and passed straight to the network (no cache lookup). This ensures the version check always gets the real server version, even when the old SW is still controlling the page.

**iOS bfcache:** A `pageshow` listener with `event.persisted` check catches Safari restoring the page from back-forward cache (which doesn't fire `visibilitychange`).

### 8. Cache-First Navigation

Navigation requests (HTML) use cache-first with background revalidation:

```text
Cache hit  → serve instantly, background-fetch to update cache
Cache miss → fall back to network (same as before)
```

This makes online loads as fast as offline loads. Version mismatches are caught by `verifyVersionFresh()` within ~200ms (while the app-loader is still visible).

**Safari `redirected` fix:** Cached navigation responses from Netlify redirects have `redirected: true`, which Safari rejects. The `cleanResponse()` helper in `service-worker.js` creates a clean `Response()` copy that strips this flag. Applied at both cache-write and cache-read time.

### 9. Build-Accurate Manual Update Surfaces (v2.249)

The manual update paths were rewritten to compare the running **build** against the deployed version, instead of the old active-SW-vs-waiting-SW comparison (which falsely reported "up to date" whenever the SW was current, even if the rendered HTML/CSS were a stale build):

- **`checkForUpdates()`** fetches the deployed version via the new `fetchServerVersion()` (`version.js` with `cache: 'no-store'`) and compares it to `getBuildVersion()`. It reports "up to date (vX)" **only** when `build === server`; otherwise it offers a real update via `applyUpdateAndReload()` (clears caches + unregisters the SW + reloads to `?_cb=<timestamp>`).
- **`forceServiceWorkerUpdate()`** (the settings + main-menu "Check for Updates" button) now just delegates to `checkForUpdates()`. The now-unused `getWaitingWorkerVersion` helper was removed.
- **About modal** (`modalManager.js`) now shows the build version (`getBuildVersion()` / `<meta>`), not `globalThis.APP_VERSION`.
- **Pull-to-refresh** (`defaultRefresh` in `pullToRefresh.js`) now dispatches the `app:verifyVersion` event so an explicit refresh gesture gets the latest build (heals stale HTML/CSS), not just a data re-render. It stays `window.*`-free by using an `app:*` CustomEvent.

## What Happens for Existing Users

### First Visit After Update

1. Page loads with old service worker (cache-first — instant)
2. `verifyVersionFresh()` fetches `version.js` from server (bypasses SW)
3. Detects `CACHE_VERSION` mismatch → clears all caches → reloads
4. Reload loads fresh content from network → new SW installs
5. Subsequent loads use cache-first with new content

### iOS PWA Reopened After Update

1. Safari restores page from memory/bfcache (old content)
2. `pageshow` or `focus` event triggers `verifyVersionFresh()`
3. Detects version mismatch → clears caches → reloads
4. App-loader visible during reload — user sees smooth transition

### All Future Visits

1. Page loads with versioned SW (cache-first — instant)
2. Background checks every 60 seconds + on tab focus
3. `verifyVersionFresh()` runs on every focus/visibility change
4. Update detected → automatic cache-clear + reload

### Stale Build Self-Heal (v2.249+)

1. Device is rendering a stale cached HTML/CSS build even though `version.js` (→ `APP_VERSION`) reads the latest deployed version
2. `verifyVersionFresh()` compares the HTML's `<meta>` build version against the freshly-fetched server `version.js` → detects `buildStale`
3. Clears ALL caches + unregisters the SW → reloads to `?_cb=<timestamp>` (fresh from network)
4. Loop guard (`sessionStorage['__miniCycle_buildHeal']`, keyed on server version) prevents reload loops if the cache still can't refresh; a fresh launch retries

> **Caveat:** The self-heal only protects a device once it is **already on 2.249+**. A device stuck on a pre-2.249 build still needs a one-time manual cache clear / PWA reinstall to first load 2.249. See the copy-paste console snippet in [FIX_3_STALE_CACHE.md → Manual recovery](../developer-guides/FIX_3_STALE_CACHE.md#manual-recovery--force-clear-a-stuck-device).

## Server Configuration (Netlify)

Cache headers are configured in `netlify.toml` (last-match-wins ordering):

| File Pattern | Cache-Control | Why |
|---|---|---|
| `*.js`, `modules/**/*.js` | `public, max-age=86400` | 24-hour browser cache for offline support |
| `*.css` | `public, max-age=86400` | Same — offline support |
| `*.html` | `no-cache, no-store, must-revalidate` | Safari fix — `no-store` required |
| `/version.js` | `no-cache, no-store, must-revalidate` | Must never be cached (version source of truth) |
| `/service-worker.js` | `no-cache, no-store, must-revalidate` | Must never be cached |

**Critical ordering:** `version.js` and `service-worker.js` rules must come AFTER the general `*.js` rule because Netlify uses last-match-wins.

**Safari note:** Safari's memory cache ignores `must-revalidate`. Only `no-store` reliably prevents stale content. That's why HTML files use both.

## Safeguards

| Safeguard | What It Does |
|---|---|
| `sessionStorage` flag | Prevents repeated migration prompts |
| `refreshing` flag | Prevents multiple simultaneous reloads |
| User confirmation | Required before any reload |
| Offline guards | No cache clearing, no retry suffix, no destructive recovery when offline |
| Warm cache message | Post-boot `WARM_CACHE` message to SW verifies and fills precache gaps |
| HTML failsafe | Counts consecutive boot failures; only nukes caches when online |

## Debugging

### Check current SW version
```javascript
navigator.serviceWorker.getRegistration().then(reg => {
    console.log('Active SW:', reg.active?.scriptURL);
});
```

### Force update check
```javascript
navigator.serviceWorker.getRegistration().then(reg => reg.update());
```

### Inspect cache contents
```javascript
caches.keys().then(names => names.forEach(async name => {
    const cache = await caches.open(name);
    const keys = await cache.keys();
    console.log(name, keys.length, 'entries');
}));
```

### Check if offline guards are active
Open the app offline and look for these console messages:
- `📴 Offline fast-path:` — SW serving from cache without trying network
- `⚠️ Cache recovery skipped (offline)` — destructive recovery prevented
- `🔄 Boot failures detected but offline — skipping cache clear` — HTML failsafe skipped

## Content Security Policy

CSP uses **SHA-256 hashes** for inline scripts (not `'unsafe-inline'`). Hashes are configured in:
1. `<meta>` tag in `miniCycle.html`
2. HTTP headers in `netlify.toml`, `.htaccess`, and `nginx-security.conf`

**If you modify ANY inline `<script>` in miniCycle.html**, the SHA-256 hashes must be recomputed and synced to every location. `update-version.sh` does this automatically — its CSP hash stage detects new/changed inline scripts and rewrites the `script-src` directive in all three deployment configs. Local dev (Python server) does not send CSP headers, so this will only break in production.

> **v2.249:** The new `getBuildVersion()` inline script and the rewritten `verifyVersionFresh()` / `checkForUpdates()` / `forceServiceWorkerUpdate()` blocks changed the inline scripts, so `update-version.sh` regenerated the `script-src` SHA-256 hashes across `netlify.toml` / `.htaccess` / `nginx-security.conf`.

See [PWA_OFFLINE_ARCHITECTURE.md](./PWA_OFFLINE_ARCHITECTURE.md) § CSP Gotchas for details.

## Lessons Learned

### Service Worker Updates (v1.326)
1. Always use `updateViaCache: 'none'` — browser SW caching is a real problem
2. Version parameters force browsers to fetch new files
3. Periodic checks (60s) ensure users see updates quickly
4. User-controlled reloads (no forced refresh) improves UX

### Module Cache Duplication (v1.329–1.330)
5. Dynamic imports MUST use the same URL as static imports
6. ES6 modules cache by exact URL — `module.js` ≠ `module.js?v=1`
7. `withV()` helper centralizes versioning and prevents duplicates
8. `version.js` single source of truth propagates everywhere

### Offline Boot (v2.050–2.056)
9. iOS kills PWA service workers when the app is backgrounded
10. `no-cache, max-age=0` headers prevent browser HTTP cache fallback when SW is dead
11. Browser HTTP cache (`max-age=86400`) is the safety net when the SW isn't running
12. Never clear caches when offline — they're the only source of files
13. Never retry with a modified version suffix when offline — it misses every cache
14. Module import failures offline are NOT cache corruption — don't misclassify them
15. CSP hashes must be recomputed when inline scripts change — local dev won't catch this

### Stale Build vs Network Version (v2.249)
16. `APP_VERSION` is served network-first on a `?v=` mismatch — it's a *network* signal, not "what am I running." The honest signal is the HTML's baked `<meta name="app-version">` (the **build version**, via `getBuildVersion()`)
17. Update checks and the About dialog must trust the build version, not `APP_VERSION`, or they'll report "up to date" while rendering stale HTML/CSS
18. Healing a stale build means clearing caches AND unregistering the SW — a cache-first navigation handler can otherwise re-serve the same stale HTML
19. A session-scoped, server-version-keyed loop guard prevents reload loops when the cache can't refresh
20. The self-heal only protects devices already on 2.249+; a pre-2.249 device needs a one-time manual cache clear / reinstall first
