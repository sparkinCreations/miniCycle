## Overview

Sample routines are pre-built `.mcyc` files that appear in the **Create New Routine** dialog. They let new users load a ready-made routine instead of starting from scratch.

**User flow:**
1. Menu -> Create New Routine
2. Dialog shows a name input + "Load Sample" button
3. Clicking "Load Sample" reveals a scrollable list of samples
4. Clicking a sample imports it as a new routine

**Key design decisions:**
- **Manifest-driven** -- a `manifest.json` file lists available samples, not hardcoded JS
- **Auto-generated** -- a build script scans `.mcyc` files and produces the manifest
- **Cached per session** -- manifest is fetched once, reused on subsequent dialog opens
- **Graceful degradation** -- if the manifest fetch fails (offline, missing file), the "Load Sample" button is hidden and blank-routine creation still works

## Architecture

```
examples/sample-routines/
  ├── manifest.json              ← Auto-generated by npm run samples
  ├── getting-started.mcyc       ← Sample .mcyc files
  ├── Daily_Routine.mcyc
  ├── QA_Inspection_Checklist.mcyc
  └── ...

scripts/
  └── generate-sample-manifest.sh  ← Standalone manifest generator

modules/routine/routineManager.js
  ├── _sampleManifestCache         ← Module-level cache (fetched once)
  ├── _fetchSampleManifest()       ← Fetches + caches manifest.json
  ├── _buildCreationDialog()       ← Async; builds sample list from manifest
  └── loadSampleRoutine()          ← Loads a .mcyc file by filename
```

### Data flow

```
npm run samples
  → scripts/generate-sample-manifest.sh
    → Scans examples/sample-routines/*.mcyc
    → Extracts title + emoji from each file
    → Writes manifest.json

User opens Create New dialog
  → _buildCreationDialog() calls _fetchSampleManifest()
    → First call: fetch('examples/sample-routines/manifest.json')
    → Subsequent calls: returns _sampleManifestCache
  → Builds sample list from manifest entries
  → User clicks a sample
    → loadSampleRoutine(filename) fetches the .mcyc file
    → processImportedData() validates and imports it
```

## File Format Requirements

Every sample `.mcyc` file must be a valid Schema 2.5 routine with **all fields present**. This ensures clean imports without repair warnings in the console.

### Required root-level fields

| Field | Type | Value | Notes |
|-------|------|-------|-------|
| `name` | string | Unique identifier | e.g. `"daily_routine"` |
| `title` | string | Display name with emoji | e.g. `"☀️ Daily Routine"` -- emoji at start or end |
| `tasks` | array | Task objects | See task fields below |
| `autoReset` | boolean | `true` or `false` | `true` for repeating routines, `false` for one-time |
| `cycleCount` | number | `0` | Always 0 for samples |
| `deleteCheckedTasks` | boolean | `false` | Samples default to Cycle mode |
| `taskOptionButtons` | null | `null` | Uses app defaults |
| `recurringTemplates` | object | `{}` | No recurring templates in samples |
| `reminders` | null | `null` | No reminders pre-configured |
| `theme` | string | `"classic"` | Always classic -- user can change later |
| `createdAt` | number | Unix timestamp (ms) | Any reasonable timestamp |

### Required task-level fields

Every task object must include **all** of these:

```json
{
  "id": "task-qa-001",
  "text": "🔧 Task description here",
  "completed": false,
  "dueDate": null,
  "highPriority": false,
  "remindersEnabled": false,
  "recurring": false,
  "recurringSettings": {},
  "deleteWhenComplete": false,
  "deleteWhenCompleteSettings": {
    "cycle": false,
    "todo": true
  },
  "schemaVersion": 2
}
```

**Why all fields?** The import repair system in `routineLoader.js` logs `console.warn()` for every missing field it has to repair. Including all fields keeps the console clean and proves the sample files are complete.

### Emoji placement in titles

The manifest generator supports emoji at the **start** or **end** of the title:

```
"🍳 Classic Breakfast Burrito (Recipe)"   ← emoji at start (preferred)
"Getting Started 🚀"                      ← emoji at end (also works)
```

The script uses Python's `unicodedata.category()` to detect emoji characters and split them from the name. If no emoji is found, it defaults to a clipboard emoji (📋).

### File naming

Use `Descriptive_Name.mcyc` with underscores for spaces:

```
✅  QA_Inspection_Checklist.mcyc
✅  Opening_Closing_Procedures.mcyc
✅  Daily_Routine.mcyc
❌  qa inspection checklist.mcyc    (spaces)
❌  QA.mcyc                         (not descriptive)
```

## Adding a New Sample Routine

### Quick steps

1. Create the `.mcyc` file in `examples/sample-routines/`
2. Run `npm run samples`
3. Done -- the manifest auto-updates

### Detailed walkthrough

**Step 1: Create the .mcyc file**

Create a new file in `web/examples/sample-routines/`. Use the full Schema 2.5 format with all fields. Copy an existing sample as a template.

Key decisions:
- **`autoReset: true`** for routines people repeat (daily, weekly)
- **`autoReset: false`** for one-time processes (recipes, checklists)
- **`highPriority: true`** on critical tasks the user should not skip
- **Emoji in task text** for visual appeal and scannability

**Step 2: Regenerate the manifest**

```bash
cd web/
npm run samples
```

Output:
```
  🍳 Classic Breakfast Burrito (Recipe)
  🏃 Cardio & Core Routine
  ☀️ Daily Routine
  🔑 Opening & Closing Procedures
  🔍 QA Inspection Checklist (Machine Shop)
  🚀 Getting Started
✅ Generated manifest.json (6 samples)
```

**Step 3: Verify**

Open the app -> Menu -> Create New Routine -> click "Load Sample" and confirm the new entry appears.

### Checklist

- [ ] File is valid JSON (run `python3 -m json.tool Your_File.mcyc`)
- [ ] All root-level fields present (name, title, tasks, autoReset, cycleCount, deleteCheckedTasks, taskOptionButtons, recurringTemplates, reminders, theme, createdAt)
- [ ] All task-level fields present (id, text, completed, dueDate, highPriority, remindersEnabled, recurring, recurringSettings, deleteWhenComplete, deleteWhenCompleteSettings, schemaVersion)
- [ ] Title includes emoji (start or end)
- [ ] File named with underscores: `Descriptive_Name.mcyc`
- [ ] `npm run samples` ran successfully
- [ ] Sample appears in Create New dialog
- [ ] Clicking the sample imports it correctly

## Manifest Generation

### Standalone script

```bash
npm run samples
# or directly:
./scripts/generate-sample-manifest.sh
```

**What it does:**
1. Scans `examples/sample-routines/*.mcyc` for all `.mcyc` files
2. Opens each file and reads the `title` field
3. Extracts the emoji and name from the title
4. Writes `manifest.json` sorted alphabetically by filename

**Script location:** `scripts/generate-sample-manifest.sh`

**Output format** (`manifest.json`):
```json
[
  {
    "file": "Daily_Routine.mcyc",
    "name": "Daily Routine",
    "emoji": "☀️"
  }
]
```

### How emoji extraction works

The script uses a Python inline script with `unicodedata.category()`:

1. **Try leading emoji** -- if the title starts with emoji characters, split there
2. **Try trailing emoji** -- if the title ends with emoji characters, split there
3. **Fallback** -- if no emoji found, use the clipboard emoji (📋) as default

Characters are considered emoji if `unicodedata.category(c) == 'So'` (Symbol, Other) or `ord(c) > 0x1F000`.

### When to run it

- After adding or removing a `.mcyc` file from `examples/sample-routines/`
- After changing a sample file's `title` field
- As part of a version update via `update-version.sh --samples`

You do **not** need to run it if you only changed task text or other non-title fields.

## Integration with update-version.sh

The version updater script (`scripts/update-version.sh` v5.4+) has a `--samples` / `-s` flag:

```bash
# Regenerate manifest as part of a version update
./scripts/update-version.sh --samples

# Combine with other flags
./scripts/update-version.sh --auto --samples

# Standalone is easier for quick updates
npm run samples
```

**Behavior:**
- In normal (interactive) mode: prompts whether to regenerate the manifest
- In `--auto` mode with `--samples`: regenerates automatically without prompting
- In `--lite-only` mode: skipped (lite version has no sample routines)
- In `--dry-run` mode: shows what would happen without writing

**When to use which:**
- **`npm run samples`** -- quick, standalone, just regenerates the manifest
- **`--samples` flag** -- convenient when you're already doing a version update

## UI Behavior

### Create New Routine dialog

The dialog has two views that swap via CSS:

**View 1 (Name Input):**
- Text input for routine name
- "Load Sample" button (only shown if manifest has entries)
- Create / Cancel buttons

**View 2 (Sample List):**
- Back arrow button to return to View 1
- Scrollable list of samples from manifest
- Each sample shows: emoji + name

### Scroll limit

The sample list has a CSS max-height for scrolling:

```css
.sample-list {
    max-height: 260px;
    overflow-y: auto;
}
```

This fits approximately 4-5 items before scrolling. With 6+ samples, the list scrolls gracefully without pushing the dialog off-screen.

### Caching

The manifest is fetched once per session and cached in a module-level variable (`_sampleManifestCache`). Opening the Create New dialog multiple times reuses the cached manifest without additional network requests.

## Graceful Degradation

If the manifest fetch fails (network error, file missing, invalid JSON):

1. `_fetchSampleManifest()` catches the error and returns `[]`
2. `_buildCreationDialog()` sees an empty array
3. The "Load Sample" button is **not added** to the dialog
4. The entire sample list view (View 2) is **not created**
5. The name input view (View 1) works normally for creating blank routines

**Console output on failure:**
```
⚠️ Failed to load sample manifest: 404
```

This means sample routines are a **progressive enhancement** -- the core Create New dialog always works, even offline or if the manifest is missing.

## Import Repair System

When a sample `.mcyc` file is loaded, it passes through two validation layers:

### 1. Import validation (`cycleImportManager.processImportedData`)

- Sanitizes text (HTML stripped, length limited to 150 chars)
- Validates task structure
- Sets defaults for any missing fields
- Resolves theme (downgrades locked themes to `'classic'`)
- Sanitizes `taskOptionButtons` and `reminders`

### 2. Load-time repair (`routineLoader.repairAndCleanTasks`)

- Validates and repairs all cycle-level fields (title, cycleCount, autoReset, deleteCheckedTasks)
- Validates and repairs all task-level fields with `console.warn()` for each repair:
  - Missing/invalid ID, text, completed, highPriority, remindersEnabled, recurring
  - Missing dueDate, recurringSettings, schemaVersion
  - Missing deleteWhenCompleteSettings
- Syncs `deleteWhenComplete` with the current mode

**This is why sample files should include all fields** -- it prevents a wall of repair warnings in the console every time someone loads a sample. With complete files, the repair system has nothing to fix.
